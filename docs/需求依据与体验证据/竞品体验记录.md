# 竞品体验记录

> 项目：面向首次准备实习大学生的 AI 求职准备助手  
> 体验对象：牛客 AI 岗位辅导师、ChatGPT  
> 体验角色：林浩（虚构模拟案例）  
> 体验目的：观察现有 AI 产品在“岗位差距判断 → 用户纠错 → 下一步行动”这一场景中的实际表现，并为本产品的功能取舍提供依据。

---

# 1. 体验说明

本次体验不模拟真人访谈，也不将 AI 输出内容作为用户研究结论。

体验过程中，牛客 AI 岗位辅导师和 ChatGPT 使用尽可能一致的输入，包括：

- 相同的目标岗位 JD；
- 相同的林浩基础信息；
- 相同的项目经历；
- 相同的用户纠正信息；
- 相同的“只规划未来 7 天”的要求。

通过控制输入条件，重点比较以下问题：

1. 是否能够理解用户经历；
2. 是否能够识别用户与目标岗位之间的差距；
3. 是否能够给出明确优先级；
4. 是否区分用户事实、AI 推测和未知信息；
5. 用户纠正后，建议是否会发生合理变化；
6. 建议是否容易理解和回看；
7. 是否能将建议进一步转化为明确行动。

本次体验仅代表本次实际操作结果，不代表所有用户在所有场景下的体验。

---

# 2. 统一测试案例

## 2.1 目标岗位

Java 后端开发实习生。

岗位主要要求包括：

- Java 基础语法、面向对象、集合；
- 对多线程有一定了解；
- Spring / Spring Boot；
- MyBatis；
- MySQL 基础操作、索引和事务；
- Redis；
- Git；
- Linux 常用命令；
- 基本数据结构与算法；
- 完整 Java 后端项目经历优先。

---

## 2.2 初始用户信息

林浩，大三上学期，软件工程专业，第一次正式准备实习。

计划约 4 个月后开始投递 Java 后端开发实习，每周约可投入 20 小时。

当前明确提供的信息：

- 学过 Java 基础语法、面向对象、集合；
- MySQL 会基础增删改查；
- Git 会 add、commit、push；
- 做过少量数组、字符串基础算法题；
- 做过学校课程项目“学生信息管理系统”；
- 项目使用 Java、MySQL、JDBC；
- 实现增删改查、登录、成绩查询；
- 项目仅在本地运行。

首次输入时，用户没有主动说明 Spring Boot、Redis、Linux、多线程等能力状态。

---

## 2.3 后续统一纠正

随后统一补充：

> 我其实刚学完 Java 集合，多线程还没有学。MySQL 也只会基础的增删改查，不了解索引和事务。之前的学生信息管理系统只是学校 JDBC 作业，我并没有真正做过完整的 Java 后端项目。按照这个情况，我现在应该算 Java 初学者。

最后统一要求：

> 如果只确定未来 7 天最值得做的一件事，请不要把所有 Java 后端知识都塞进来，只保留这个阶段最重要的内容，并说明完成标准。

# 3. 牛客 AI 岗位辅导师体验

## 3.1 入口与产品形态

### 实际观察

牛客的 AI 岗位辅导师入口位于页面右侧区域。

本次体验中，我最初习惯从页面顶部和主要导航区域寻找 AI 相关入口，没有立即找到，最后从右侧区域进入。

进入以后，产品主体仍然是一个聊天窗口：

- AI首先发起话题；
- 用户继续通过自然语言输入；
- AI通过连续对话给出建议；
- 历史会话可以保留；
- 可以创建多个对话。

### 本次体验感受

入口对第一次使用的用户并不十分突出。

这一点属于本次个人实际体验，尚不能据此判断其他用户是否也会遇到相同问题。

---

## 3.2 输出速度

### 实际观察

牛客 AI 的生成速度较快。

在本次测试中，岗位分析、差距分析和行动计划都能够较快返回。

### 对产品的启发

求职准备场景并不一定需要长时间等待复杂结果。

因此，本产品的模拟 AI 处理中状态应保持简洁，不需要通过过长等待制造“AI 很复杂”的感觉。

---

## 3.3 信息理解与差距分析

### 实际观察

牛客能够结合用户提供的 JD 和个人经历进行分析。

首次输出能够：

- 列出已经满足的要求；
- 列出缺失能力；
- 给出阶段性优先级；
- 给出约 4 个月的学习规划。

内容整体分条较清楚，可读性尚可。

### 值得注意的问题

在用户首次并未说明多线程、Spring Boot、MyBatis、Redis、Linux等状态时，牛客直接将其中多项判断为“尚未接触”“不了解”或“没有涉及”。

也就是说，本次体验中出现了：

> 用户没有提供某项信息 → AI直接倾向于判断为缺失能力

而不是先将其保留为“暂时未知”。

这成为本产品设计“Unknown / 待确认”状态的重要依据之一。

---

## 3.4 用户纠正后的变化

### 实际观察

当用户明确补充自己：

- 多线程没有学；
- MySQL只会CRUD；
- 学生管理系统只是JDBC课程作业；
- 当前属于Java初学阶段；

牛客能够接受这些新信息，并重新调整学习优先级。

它同时能够解释：

- 哪些建议发生变化；
- 为什么调整多线程优先级；
- 为什么改变项目推进节奏。

因此，牛客并不是无法处理用户纠错。

### 发现的不足

虽然建议发生了变化，但这些变化仍然主要存在于两段聊天文本中。

用户需要自己对比：

- 上一次建议；
- 本次建议；
- 哪项事实改变；
- 哪项优先级发生变化。

产品没有将“修改前 → 修改后”形成稳定的结构化差异展示。

---

## 3.5 7天行动计划

牛客最终给出的未来7天核心行动是：

> 学习 Spring Boot + MyBatis，并将原学生信息管理系统中的 JDBC 数据访问部分替换为 MyBatis。

计划按照 Day 1～Day 7进行拆分，并提供完成标准。

### 优点

- 有明确时间范围；
- 有阶段任务；
- 有完成标准；
- 相比长期4个月规划，更接近可执行任务。

### 本次体验中的问题

行动仍然主要以一段聊天文本的形式存在。

用户无法直接看到：

- 当前选择的是哪一个正式行动；
- 行动是否已经开始；
- 当前完成到什么阶段；
- 哪些任务已经完成；
- 行动结果之后会如何影响原来的岗位差距。

因此“建议”已经比较清楚，但“行动状态”仍然主要依赖用户自己管理。

---

# 4. ChatGPT 体验

## 4.1 产品形态

ChatGPT 同样以连续对话作为主要交互方式。

用户可以直接用自然语言输入：

- JD；
- 个人经历；
- 补充说明；
- 用户纠正；
- 后续任务要求。

这一方式的信息输入自由度较高。

---

## 4.2 信息理解能力

### 实际观察

ChatGPT能够比较完整地理解用户提供的背景，并将 JD 拆分为多个能力维度进行对照。

首次分析中，它使用表格展示：

- JD要求；
- 林浩当前情况；
- 当前判断。

随后又将能力分为 P0 / P1 / P2，并给出4个月路线。

相比单纯段落回答，结构已经比较清晰。

---

## 4.3 未知信息处理

首次分析时，林浩没有主动说明：

- 多线程；
- Spring Boot；
- MyBatis；
- Redis；
- Linux。

ChatGPT在第一次输出中，将多线程、Spring Boot、MyBatis、Redis等多项“未提及”的能力直接标为了明显缺口或需要补充。

Linux也被首次判断为需要补基础。

用户纠正后，第二次分析中的 Linux 状态改为了：

> 暂无法确认。

这说明 AI 在获得更明确指令或上下文后能够更谨慎地处理未知信息，但首次输出仍然存在：

> 未提及的信息被较快转化为负面能力判断

的问题。

这与本产品“未提及 ≠ 不会”的设计原则直接相关。

---

## 4.4 用户纠正能力

### 实际观察

在用户明确纠正自己的真实水平后，ChatGPT能够：

- 承认第一次判断高估了后端实践能力；
- 将用户定位从“已有后端入门基础”调整为“Java初学者 / 后端准备初期”；
- 下调课程项目的能力证明强度；
- 调整技术学习顺序；
- 解释为什么建议发生变化。

这一点表现较好。

### 仍存在的问题

纠正前后的内容仍然存在于不同聊天消息中。

用户如果希望回答：

> “究竟是哪一条事实改变导致哪一项建议变化？”

仍然需要阅读和对比较长文本。

---

# 5. ChatGPT 的7天行动表现

ChatGPT最终将7天目标收敛为：

> **只学习 Java 多线程基础，并完成一个多线程小练习。**

计划包含：

- Day 1～Day 7安排；
- Thread；
- Runnable；
- 线程安全；
- synchronized；
- 线程池基础；
- 多线程售票小练习；
- 明确完成标准。

这一结果与牛客明显不同。

牛客认为：

> 7天优先进入 Spring Boot + MyBatis。

ChatGPT认为：

> 7天只先补 Java 多线程基础。

两者均基于相同 JD、相同人物信息和相同纠正内容，却得出了明显不同的短期优先级。

### 对本产品的启发

本次体验说明：

**AI能够给出建议，并不意味着“下一步”天然具有唯一正确答案。**

因此用户真正需要的不只是一个结论，而是：

- AI为什么这样判断；
- 使用了哪些用户事实；
- 哪些仍然属于推测；
- 为什么这一项比其他事项优先；
- 用户是否认可这个优先级；
- 用户能否调整后再形成自己的行动。

这也是本产品不直接把 AI 输出作为不可修改最终答案的原因。

---

# 6. 两个产品的共同特点

根据本次实际体验，两者都具备以下能力：

1. 可以接收较复杂的自然语言信息；
2. 可以结合 JD 分析用户能力；
3. 可以给出能力差距；
4. 可以生成优先级；
5. 用户补充新信息后，可以重新调整建议；
6. 可以生成短期学习计划；
7. 都支持持续多轮对话。

因此，本产品不能简单把竞品问题描述为：

> “现有 AI 不会做岗位差距分析。”

这一说法与实际体验不符。

---

# 7. 本次体验中共同存在的问题

## 7.1 核心信息主要存在于聊天文本中

虽然两者都能使用：

- 表格；
- 分点；
- Markdown；
- 优先级；

改善阅读体验，但产品本质仍然以“AI消息”为主要承载方式。

随着对话增加，以下信息逐渐分散：

- 用户事实；
- AI推测；
- 尚未知的信息；
- 第一次诊断；
- 用户纠正；
- 新诊断；
- 当前行动。

---

## 7.2 用户需要自己完成前后信息比较

两者都能在用户纠正后调整答案。

但“变化”没有成为一个稳定的独立产品对象。

例如用户仍需自己理解：

> 原来为什么推荐Spring Boot  
> → 我补充了什么  
> → 为什么现在改成多线程  
> → 哪一项能力状态发生变化

---

## 7.3 建议存在，但行动管理较弱

两者都可以输出非常具体的7天计划。

因此本产品不能声称：

> “普通 AI 无法给出行动计划。”

真正的差异是：

普通对话中的计划主要仍是一条消息。

本产品希望进一步将其结构化为：

> **诊断 → 用户选择 → 当前行动 → 执行状态 → 行动反馈 → 新事实 → 下一阶段建议**

---

## 7.4 长回答增加信息读取成本

尤其在完整岗位分析场景中，两类 AI 都可能一次输出较多内容。

即使回答质量较高，首次准备实习的用户仍需要在大量文本中寻找：

> 我现在到底最该做什么？

因此本产品在界面上将：

- 能力状态；
- 优先级；
- 建议依据；
- 当前行动；

拆分为不同层级，而不是全部塞入单条 AI 回复。

---

# 8. 对本产品设计的影响

根据本次真实体验，本产品最终没有选择“做一个更专业的求职聊天机器人”，而是针对对话式 AI 已经具备但展示不足的部分进行产品化。

## 8.1 信息三态

设计：

- Confirmed｜已确认事实
- Inferred｜AI推测
- Unknown｜待确认

对应本次体验中出现的：

> 用户未提及某项能力，但 AI 已经倾向于判断为缺口。

---

## 8.2 建议依据独立展示

每项主要建议均允许查看：

- 对应 JD；
- 使用的用户事实；
- AI推测；
- 排序原因。

避免用户只能在长消息中寻找理由。

---

## 8.3 用户纠错成为正式流程

不是继续输入一句：

> “你理解错了。”

而是提供明确的“不准确 / 纠正”入口。

纠正后的事实进入统一信息源，并重新生成诊断。

---

## 8.4 建议变化可视化

不只重新输出一段新回答，而是显示：

> 原判断 → 新判断

并说明变化依据。

---

## 8.5 将建议转化为当前行动

用户从多个能力差距中选择当前阶段真正要执行的行动。

系统展示：

- 当前行动；
- 行动目标；
- 完成标准；
- 当前阶段。

不使用“岗位准备度 72%”等缺少真实依据的伪精确进度。

---

## 8.6 行动结果重新进入诊断

行动结束后，不只标记“任务完成”。

用户反馈实际掌握情况后，系统将结果转成新的事实，并进一步更新：

- gap；
- partial；
- met；
- unknown；

以及下一阶段建议。

这样形成：

> **判断 → 行动 → 新事实 → 新判断**

的闭环。

---

# 9. 本次体验结论

本次体验没有发现牛客或 ChatGPT “无法提供求职建议”。

相反，两者均能够完成较好的岗位分析、差距识别和学习规划。

本产品真正希望解决的问题是：

> **当 AI 已经能够给出建议以后，怎样让用户更容易理解 AI 使用了什么信息、发现错误、完成纠正、判断优先级，并把建议持续转化为下一步行动。**

因此，本产品的价值重点不是生成更多文字，而是将 AI 求职建议进一步产品化为：

**可理解、可纠正、可追溯、可行动的准备流程。**
